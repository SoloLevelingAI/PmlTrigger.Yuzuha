# 三条并列方案怎样比较

共同目标是从需求开始规定架构，再从零建立应用；本轮先交付可审阅材料。LikeC4 图稿冻结，OpenSpec 与 Archon 各自独立设计。工具不强制某种模块结构，下面是本轮设计选择。

| 路径 | 当前审阅入口 | 本轮着重解决什么 | 需要继续防止什么 |
| --- | --- | --- | --- |
| LikeC4 | 原 architecture/aspire-like、architecture/aspire 两分支的三张入口图 | 快速看整体关系、职责与编排差异；本轮原样保留 | 图上连线不自动证明实现正确；现稿的源码映射不能自动变成重写方案 |
| OpenSpec | architecture/openspec 的 proposal → 场景规范 → design → tasks | 先规定用户可观察的行为；用功能切片承担目录、资源、启动与交付 | 跨切片共享接口不断膨胀、场景存在却没有真正实现 |
| Archon | architecture/archon 的范围 → 设计 → 反例审阅 → 检查 → 用户审阅 | 以薄操作协调器和结果证据组织任务、失败与恢复 | 协调器成为大类、把工作流编排误当成产品必需的后台服务 |

## 相同输入和约束

OpenSpec 与 Archon 使用逐字相同的 PRODUCT-BRIEF.md，含 R01–R14。每份候选各有 27 个可观察场景、拟议逻辑依赖和未来实现任务。两份都保留 WPF / .NET 10、独立 EXE、旧数据兼容、视觉核对、可替换 Aspire 开发适配器和未来多机边界。

LikeC4 的现稿不在本轮修改。若之后选定它，也须先确认从零实现的计划，不能把旧稿中的逐步拆分建议直接当成已批准任务。

## 阅读顺序

1. 确认共同需求是否有遗漏。
2. 比较“功能各自拥有运行结果”与“薄协调器统一任务结果”哪种更易理解和维护。
3. 阅读同一类反例：许可闪断、入口交接、部署断电、跨机导入与数据目录不可用。
4. 选定或修订候选后再实现。不要因为工具显示规划 complete 或校验 passed，就把架构当成已批准。

## 校验能证明什么

OpenSpec 的严格校验验证规范结构；Archon 官方 schema 验证工作流定义。本地检查验证本轮拟议逻辑依赖、无环、需求映射和文档证据，并用故意违规验证检查会失败。

这些不是已重写程序集的测试，也不是三种工具自动生成的架构优劣评分。Archon 后续已实际执行六个串行 Codex 阶段，并通过原生 --adopt 保留失败、修订和复核证据，最终停在人工审阅；见 [当前入口](README.md)。OpenSpec 与 LikeC4 保持原分支。应用行为、兼容数据和视觉验收仍待实现后完成。
