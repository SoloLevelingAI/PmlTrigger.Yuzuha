# 主要决策与反例审阅

所有决策为草案，未得到实现批准。下面的反例是本轮设计审阅记录，不是运行了 AI reviewer 的声明。

| 决策 | 考虑的替代方式 | 本候选的理由 | 必须观察的失败信号 |
| --- | --- | --- | --- |
| 本机模块化单体 | 常驻 Web API 与远程控制平面 | 单人桌面使用和离线能力优先，先降低部署成本 | 无网络打不开本机界面 |
| 薄操作协调器 | 所有功能各自维护任务状态 | 启动与更新需要一致的结果、取消和恢复入口 | 协调器开始包含文件/许可业务细节 |
| 有限请求协议 | 通用脚本插件与任意动作 JSON | 控制可执行范围，后续设备协议可版本化 | 导入配置可执行命令，Worker 可随意启动程序 |
| 本机 JSON + 回执 | 第一版就引入数据库服务器 | 当前数据量和本机工作模式不需要常驻数据库 | 多进程冲突被静默覆盖；回执与操作不关联 |
| Aspire 为开发适配器 | 将 AppHost 当成产品必需服务 | 可借用诊断而保留独立桌面发布物 | 普通工作台依赖 Aspire，停止调试终止用户 VM |
| 明确保留不确定结果 | 失败就自动重试 | 外部进程和文件写入无法与本机日志形成原子提交 | 重启后重复安装、重复启动或假报成功 |

## 本轮对抗性问题与修订

1. 统一操作状态会不会把窗口出现误当成登录成功？→ 外壳 Outcome 与类型专属 Evidence 分开；会话就绪必须有提供者证据。
2. 中央协调器会不会复制现有大 ViewModel？→ 只负责排队/阶段/回执和结果投影；状态规则与副作用均在专属处理器及平台端口。
3. 旧数据是否因“从零”被清空？→ 兼容读取和稳定 ID 写入架构；迁移先预览、备份、验证，旧文件保持可恢复。
4. 全部变成事件会不会过度复杂？→ 只持久化操作必要阶段；目录使用普通快照与修订，不建消息代理或通用事件溯源系统。
5. 架构检查通过是否说明软件可用？→ 只证明逻辑依赖、需求链接与工具格式；真实进程、写入恢复和 UI 仍待实现后验收。

## 暂不进入首版

远程认证与多租户、常驻 Agent、插件市场、任意 DLL 热加载，以及从 Windows 服务直接完成 GUI 登录。这些不是遗漏功能，而是 R14 之后单独审阅的扩展范围。
