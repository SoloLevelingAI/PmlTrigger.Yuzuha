# Design

## Context

动机与取证基线见 [proposal.md](proposal.md)。当前规范已有 R/B/T/S 标识、状态机和 Roslyn 生成链；原生 CLI 的运行目录才是操作 ID、版本、输入 Schema 和授权标志的实际出口。历史项目名含 MCP，但当前交付入口是原生 CLI。

## Goals / Non-Goals

**Goals:**

- 让审查者从需求追到操作、真实符号、测试和证据环境。
- 无损保留原需求文字及 `verified` / `partial` / `planned`，将抽取解释与原文分开。
- 在明确基线下导出操作 Schema，并指出它不能代替结果数据 Schema 或真实 AVEVA 验收。

**Non-Goals:**

- 不迁移唯一规范源，不把审查快照升级为 `openspec/specs/`。
- 不修复运行行为、补齐 planned 能力、修改 API 或发布安装包。
- 不开展 AVEVA 操作、登录、部署、重建个人知识库或真人可用性测试。

## Decisions

### 1. OpenSpec 管理变更，既有 JSON 继续定义已接受要求

为纯工具接入和文档提取设置 `skip_specs: true`。审查材料位于 change 根目录，不伪造产品行为增量。直接复制成主 spec 会制造第二规范源；删除旧 JSON 则会破坏现有文档/原型/测试映射，二者均不在本次范围。

### 2. 固定基线，区分三种事实

`contract-review.md` 分开显示原规范声明、代码观察和待审决定。`evidence.json` 保存原始需求字段的可读展开、符号/测试定位与取证文件 SHA-256；源文件同时记录 Git blob 与本次 checkout 字节哈希，区分 Windows CRLF。新 JSON 快照用目录内的 `.gitattributes` 固定 LF。原 JSON 的 `baseline` 字段原样保留，另记本次实际读取的 Git 提交；不把两者混同，也不擅自更新历史基线。

`verified` 是原规范状态，不等于本轮重新验证了其中所有承诺。原来无测试绑定的条目仍显示为空；新增发现的相关测试作为补充证据标注，不自动写回 T 绑定。

### 3. 从同一编译产物导出输入契约

在隔离的 `YUZUHA_STATE_DIR` / `YUZUHA_USER_DIR` / `YUZUHA_KNOWLEDGE_DIR` / `YUZUHA_WEBAPPS_DIR` 中运行 `op list`，保留完整 JSON 外层及 46 项描述。该命令不调用业务操作；没有 PID、写入、启动或执行授权。

人工审查稿概括公共信封、授权门、目标核验、有界读取、配置修订、批处理、PML 文件流程、知识与日志边界；精确输入细节引用 JSON，不再手写一套 Schema。结果类型仍需结合 `OperationResult`、具体返回类型和测试理解。

### 4. 证据按环境分层

本轮 .NET 测试覆盖隔离文件和合成 Host；文档构建覆盖静态追溯与原型结构。既有 `docs/validation/2026-10-24-launch-cli.summary.json` 是历史证据，公开结论限 E3D 2.1，不是本轮执行回执。NET35/NET48 在缺少对应本地 SDK 时的静态分析省略项必须随验证结果披露。

### 5. 审查决定留在任务中

审查者先决定原文是否准确、证据是否足够、哪些状态需要调整，以及是否另行迁移规范源。契约接受、状态调整、迁移和未来行为修改分别记录；生成完文件不能代表人工批准。详细待审问题见 `contract-review.md`。

## Risks / Trade-offs

- 固定快照会随代码变化变旧 → 每份证据携带提交和哈希，后续以同一方法重新提取，不手工维持双份规范。
- 运行目录只有输入 Schema → 明确输出由异构业务类型组成，不声称已提取所有跨运行时二进制/RPC/安装协议。
- 历史 `verified` 容易被误读为全面实机通过 → 保留原状态并单列本轮测试、历史实机和缺证范围。
- 生成的 Codex 技能可能尚未出现在现有会话列表 → 在仓库中重新加载/重新打开 Codex 后选择技能；也可明确要求按对应技能文件运行。

## Migration Plan

本次仅新增配置、技能与审查材料，无运行时迁移。若撤销接入，移除本次新增目录即可，已有契约、用户数据和生产配置不受影响。后续如迁移唯一规范源，须另行设计 R/B/T/S 保真、生成链兼容和回退方案。
