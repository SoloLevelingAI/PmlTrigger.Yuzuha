# 修改与宏文件工作流

中文 | [English](file-macro-workflow.md)

进行改名、属性修改、批量修改，或通过 `!!YuzuhaTriggerCommand` 执行 PML 文件时，
先阅读本参考。

## 规划修改范围

1. 编写命令前读取目标及相关成员。
2. 枚举目标字符串命中的字段，并让用户确认范围：仅当前元素、指定属性，还是包括成员。
3. 修改时优先使用已经验证的 DBREF。名称可能包含看似继承、实为历史残留的路径段，
   不一定是可靠标识。
4. 保存原始 Name、Description、Owner，以及验证或人工恢复所需的其他属性。

父元素和成员的 Name 独立存储；父元素改名并不表示成员名称会自动变化。

## 编写 PML

改名通常要求新名称带前导 `/`：

```pml
!!CE = =24104/12345
!!CE.NAME = '/NEW-NAME'
!!CE.Description = 'New description'
```

上面的 DBREF 和属性值只是语法示例，必须替换为活动模型中实际验证过的值。
将用户输入放入宏之前，必须正确处理 PML 字符串转义。

修改位置时应显式指定 `WRT` 参考系；修改型宏不能依赖开始执行时碰巧存在的 CE。

## 执行文件

宏内容变化时使用新路径，例如修改 `rename_v1.pmlmac` 后写入
`rename_v2.pmlmac`。实际观察中，AVEVA `$M` 可能复用与旧路径关联的内容。

```pml
!!YuzuhaTriggerCommand.InitArgs('C:\Approved\rename_v1.pmlmac')
!!YuzuhaTriggerCommand.execute('ExecuteFile')
!!YuzuhaTriggerCommand.Query()
```

每一行必须作为单独的 `run_pml_command` 调用发送。尤其不能把 `InitArgs` 和
`execute` 用逗号或分号拼成一条命令；实测这种合并会导致 `Command.Run` 失败。

只能执行用户明确要求且内容已知的文件。执行型调用只发送一次，超时后禁止自动重试。

## 三级验证

1. **传输层：**收到 RPC 响应，只能证明通信完成，不能证明宏体成功。
2. **包装层：**读取 `Query()`；普通字符串数组可能进入 MCP 响应的 `Unparsed`，
   而不是 `Items`。
3. **模型层：**重新读取每个目标 DBREF，将实际属性与用户批准的目标值对比。
   这是权威判据。

不能用一条包装器成功消息证明宏中每一行都已完成。宏不是事务：后续行失败时，
之前的修改可能已经保留。任何失败后都必须先重读，再判断是否可以安全纠正。

## 高效查询

优先使用小结果预算、小深度和定向路径：

| 目的 | 建议起点 |
|---|---|
| 身份和直接属性 | `(10,2,'')` |
| 成员列表 | `(20,2,'member')` |
| 指定成员 | `(20,2,'member.N')` |
| 位置分支 | `(10,1,'hpos')` |
| 仅在确有需要时全量摸底 | `(100,3,'')` |

这些只是起点，不是固定上限；第一次读取证据不足时再增加。

某个属性不适用于当前元素而形成的 `Unparsed`，不会自动推翻已经确认的核心属性；
但也不能一概忽略所有 `Unparsed`，应保留警告并结合上下文判断。

## 现场状态约束

- `$P /SITE/...` 是打印，不应当作 CE 定位。通过已部署的命令对象执行路径命令后，
  用 `YuzuhaReadCurrentElement` 重新确认 CE。
- PML 名称可能区分大小写。Owner、完整名称和查询路径必须复制自最近一次读取结果，
  不要把 `/AGENT1` 自行改写成 `/Agent1`。
- 不得为了解决建模命令失败而执行 `DESIGN` 或切换模块。模块切换可能重启当前项目、
  清空上下文并使心跳从 `Degraded` 变为 `Disconnected`。
- 连接断开时停止修改型命令；等待心跳恢复并重新读取现场状态，不得自动重试。
