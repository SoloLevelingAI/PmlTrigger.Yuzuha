## 候选比较

### A1 · 直接按用例组织的模块化单体

WPF ViewModel 调用配置、启动、许可监测、工具更新、变量管理和导入导出等用例；每个用例自行管理状态、持久记录及恢复。领域规则与系统访问通过接口隔离，由普通 EXE 或 Aspire 开发入口装配。

收益：结构直接，配置 CRUD、搜索和本机绑定容易实现与测试，初期抽象成本较低。；离线运行不依赖编排平台；替换组合根和诊断适配器即可支持两种入口。；可以通过各用例自己的日志、恢复逻辑与共享状态仓库满足崩溃恢复和跨页面观察要求。

代价：启动、部署、变量应用各自处理取消、冲突、持久记录和恢复，容易重复或产生不一致。；UI 需要整合多套进度与结果模型，跨页面观察及重启后状态说明的维护成本较高。；能够满足 R09，但部署用例仍须独立承担完整的预览、备份、写入日志、互斥与恢复协议；直接组织并不能省去这些复杂度。

未选理由：可行，但 R07、R09、R10、R12 同时要求可观察状态、明确副作用和中断诊断。将这些机制分散到各用例中，长期一致性成本高于建立有限的公共协调机制。

### A2 · 按用例分模块，并显式协调有副作用操作的生命周期

保留按用例组织的模块化单体；启动、工具部署、持久变量应用及迁移使用显式操作协调器。协调器统一操作标识、持久检查点、并发准入和状态发布，各模块拥有自己的状态机及恢复规则。配置 CRUD 和只读发现保持简单调用路径。

收益：UI 通过统一操作查询订阅跨页面观察状态，同时保留启动、部署和变量操作各自的业务含义。；崩溃后可定位最后可靠检查点，将未完成操作呈现为待核验或待恢复，避免自动重放写入。；协调器作为本机 .NET 组件运行，普通 EXE 不需要网络、Aspire 或常驻远程服务。；普通入口与 Aspire 开发入口复用相同用例、状态机、配置契约及行为测试，仅替换组合根与诊断适配器。

代价：需要设计操作记录版本、检查点、事件顺序、订阅重连和恢复协议，首期成本较高。；文件系统、进程和持久环境无法形成一个原子事务，必须明确记录与外部副作用之间的不确定窗口。；若把所有操作塞入同一个状态枚举或通用工作流引擎，会掩盖业务语义，因此必须限制公共协调层的职责。

未选理由：已选
